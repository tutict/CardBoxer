0. 一句话结论
====================================================================
**静态资产能搬，驱动链全丢。** glTF 把 64k 高模、UV、3 张 4096² PBR、
13 骨骨架都完整搬进 Godot 4.5（导入零报错），但 SURFACE_DEFORM 没有
glTF 对应物，导出即烘焙成「当前帧静态快照」；228 帧动作表在源 .blend
里本来就没有 Action，于是 GLB 0 animation、Godot 0 AnimationPlayer；
高模在 Godot 里 `skeleton_path=''` / `skin_present=False`，手动转骨架
只会动那个 20k 顶点的体素化代理壳，不是角色本体。

结论：C 路线作为「导入可行性」是通的，作为「把可驱动角色接进游戏」
不成立。要真进游戏，得在 Godot 侧重建整套驱动层，或退回 C 路线渲
2D 精灵图集。本轮没做 Creative Review、没进可运行游戏工程。

口径                   体积          meshes skins anims imgs skinned verts  耗时

foe-stance.glb          2,531,012   1      0     0     0    0       64,062 0.066s
foe-posed.glb           2,533,600   1      0     0     0    0       64,143 0.085s

· foe-full 的两个 primitive：高模只有 [NORMAL, POSITION, TEXCOORD_0]；
  代理壳才有 [JOINTS_0, NORMAL, POSITION, TEXCOORD_0, WEIGHTS_0]。
· skin joints = 14 = 13 骨 + glTF 导出器自动加的 neutral_bone。
· PBR 三通道实测全在：baseColorTexture=1 / metallicRoughnessTexture=2
  / normalTexture=0；extensionsUsed=['KHR_materials_specular']。
· 站架 vs cross#10（增益 x1.5）两份都 export_apply=True：
  POSITION min/max 最大分量差 0.187166 m，而两者 skins=0 / anims=0。
  → SURFACE_DEFORM 被烘焙成两个不同的静态姿势，不是可驱动网格。
  顶点数 64,062 → 64,143 不相等，是应用修改器后 glTF 拆顶点所致，
  判据只要求「有非零位移」，不假装拓扑守恒。

**订正一处预判**：我原以为 3 张 4096² 会被重编码。实测
源 packed 合计 39,097,625 B，GLB 内 image bufferView 合计
39,097,625 B，**逐字节相同、零重编码、零降分辨率**，占
foe-full.glb 的 91.08%。想省体积只能换贴图分辨率/压缩格式，
和 glTF 导出器无关。

**订正第二处预判**：导出器两条告警都不能当成「丢东西」——
「More than one shader node tex image used for a texture」只是采样器
参数取第一个，三通道在 GLB 和 Godot 里都在；「more than 4 joint
vertex influences」只影响代理壳权重精度（截断到 4 并归一化），
不影响角色本体（本体根本没 skin）。

7. 踩坑（可复用）
====================================================================
· Godot 4.5 的 Skeleton3D **没有** Godot 3 的
  force_update_all_dirty_bones()。GDScript 里调它会在 _init() 抛
  SCRIPT ERROR，导致 quit() 不执行、SceneTree 无限空转（第一次跑挂了
  180s）。驱动脚本因此加了 60s timeout + 部分 stdout/stderr 落盘，
  否则根因会被「挂住」两个字盖掉。
· 「能不能驱动」的判据必须用 get_bone_pose_rotation（本地 pose，写入
  即读回）；get_bone_global_pose 在 headless 单帧里脏标记未刷新，
  且绕骨骼自身轴旋转本就不改 origin。第一版拿 global Transform3D
  判等得到 false，是判据口径错，不是数据坏。
· 成本账板第二列第一版按 9 项算固定行距，实际列了 14 项，尾部两段
  文字直接压在一起；看图复核抓到，改成三段各自显式推进 y。
· 文件清单必须排除 probe_project/.godot/（引擎缓存含时间戳）和生成器
  自身 stdout 日志；否则 STABLE_OK 会「一致地」记下易变文件的哈希。
  另用 %TEMP%\fa-run\ 外部脚本逐行重算清单 size + sha256。

10. 文件清单与自洽复核（收口补记）
====================================================================
make_filelist_c.py 实测：FILELIST_ENTRIES=58 /
new-files.diff=76,944 B / FILELIST_STABLE_OK（连续两次生成逐字节一致）。

**STABLE_OK 只证「两次生成一致」，不证「清单与实物一致」**，所以另写
独立脚本 crosscheck_filelist_c.py（不 import 生成器、不复用其枚举），
逐行重算 58 条的 size + sha256，并反向枚举目录查漏项：
  ROWS=58 BAD=0 EXTRA=0 / CROSSCHECK_OK
该脚本已固化进本工作区，复算命令：
  <venv>\Scripts\python.exe -u make_filelist_c.py
  <venv>\Scripts\python.exe -u crosscheck_filelist_c.py
排除口径两边一致：probe_project/.godot/ 引擎缓存（含时间戳）、
logs/make_filelist_c.log 生成器自身 stdout、清单与 diff 自身。
new-files.diff 是 14 个新增脚本/探针源码的 /dev/null → b/... diff，
便于按文件审阅本轮新增代码。

注：本节写完后清单会重跑一次（验证记录自身在清单内），重跑只改
该文件自身的 size/hash 行，条目数与 DIFF_BYTES 不变；最终仍以
logs/make_filelist_c.log 与 crosscheck 输出为准，不以本节手写数字为证。
