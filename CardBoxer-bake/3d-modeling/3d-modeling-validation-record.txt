二、成本账订正：上一轮把 B 说贵了
====================================================================
2.5D V3 记录第七节写 B 是「会引入渲染帧 vs 判定帧同步问题，天级成本」。
查盘后发现这条判断**过于悲观，须订正**：

  - `boxer_rig.py` 已经是**真 Armature**：13 根 bone、解析式两骨 IK、
    `inherit_scale="NONE"`、rest pose 就是游戏的格斗站架。
  - `baked2.json` 是这套骨架**逐帧解算读回**的关节表（12 张牌 + 3 个
    motion，每条 track 都有 `readback_error_px = 0.0`），游戏 `fighter.gd`
    消费的正是同一份 JSON。
  - 所以「渲染帧 ↔ 判定帧同步」**不是待解决问题，而是既有性质**：3D 皮肤
    由同一张表驱动，不可能漂移。三帧数值复核最坏误差 0.14 px。

真正缺的只有 mesh / 蒙皮 / 贴图三样，本轮补了前两样。
**天级成本仍在，但在后面**：完整 UV 与贴图、Godot 侧接入（ShaderToRGB
是 EEVEE 专有，卡通渲染 shader 得在 Godot 重写）、228 帧图集的抠底 /
锚点 / 打包 / 引擎换帧。别把 P0 的 16/16 读成「B 做完了」。

三、技术实现（与 2.5D 的本质差别）
====================================================================
 1. `boxer_rig.build()` 建 13 骨骨架；全部骨 `inherit_scale="NONE"`
    （原 rig 只对 8 根 IK 骨设，本模型每根骨都显式按关节距离缩放）。
 2. 13 段体块在 **armature rest 空间建模一次**，截面是圆/椭圆，绝非每帧
    重建的平面带：n1 在屏幕平面内垂直于骨轴，n2 = world +Y（侧向）。
    `RY_RATIO=0.45` 让躯干成为扁椭圆（真人胸廓），四肢 = 1.0 圆截面。
 3. 每段 vertex group 全顶点权重 1.0 + ARMATURE modifier = rigid skin。
    **逐帧不重建任何网格**，只摆骨骼。
 4. 逐帧从 baked2.json 取 11 关节 → 躯干按 hip/shoulder/head 插值出
    A..F 六点 → `boxer_rig.place()` 摆 12 根骨（`pb.matrix` + `pb.scale.y`）。
    游戏表的拉伸系数 k 就这样变成骨长缩放，刺拳 2.5x 前臂的剪影保留。
    head 骨保持 scale=1，否则头骨会把脸拉成椭圆。
 5. 41 个刚性配件（头/五官/发髻/拳套/鞋/腰带/金扣/中国结/环刃/肩甲/
    10 个关节球）按**同一张关节表**定位，不绑骨：肢体拉伸不该把球形拳套
    拉成椭球。游戏自己的 `fighter.gd` 画配件也是这个思路。
 6. 沿用 V3 街霸 IV 卡通渲染：Diffuse → ShaderToRGB → ColorRamp
    (CONSTANT 三档) → Emission；墨线/金扣不受光；11 个 toon 材质。
 7. 坐标桥一行未改：`(x, depth_y, z) = (gx/100, layer, -gy/100)`，
    ORTHO `ortho_scale=2.6` @512px = 1.96923 px/game px，相机 y=-4。

四、探针先行，以及两次「判据钉错性质」的订正
====================================================================
 `probe_rig.py` 先单渲一根骨 + 一个圆截面圆柱，确认本机 EEVEE headless
 下「vertex group 全权重 + ARMATURE modifier + `pb.matrix`/`pb.scale`」
 组合真的让网格跟随，才动主脚本。最终 `RIG_PROBE_OK`：
 逐顶点最大位移 0.3752、顶点签名不同、rest 空间 **13 个不同 y 层**
 （2.5D 平面挤出带只有 2 层）、权重和 1.0。

 两条踩过的坑，都是判据问题不是渲染问题：
  - **探针必须复现真实调用形态**：第一版用 `Matrix.Rotation(52°,'Y')`，
    其 Y 列仍是 world +Y → 骨长正对相机，渲出来只有一个圆端面。改用
    `u.to_track_quat("Y","Z")` 才是 `place()` 的真实形状。
  - **质心位移会被旋转+平移抵消**：改对调用形态后质心只动 0.0301，
    旧判据误报 FAILED；逐顶点位移其实是 0.3752。判据换成
    「顶点签名不同 且 最大逐顶点位移 > 0.15」。**要钉「顶点跟随骨骼」，
    就别拿质心当代理量。**

 【判据订正，不是调阈值放水】
  - 重复帧第一版用 `getbbox()`（阈值 >0），报了 122×60 的差异框。
    `diag_repeat.py` 实测 **max delta=1、changed_px(>6)=0** —— 是
    EEVEE 的 8-bit 量化 ±1 抖动，全文件其它差异判据都用 >6 抗锯齿
    容差，**只有这条口径不一致**。统一到 >6，并额外断言 max delta≤1。
  - 2.5D V3 的「sha 不同只因 tEXt，IDAT 完全相同」在本模型**退役**：
    圆截面曲面让 cel shading 边界落在子像素上，±1 抖动进了 IDAT。
    改为 `repeat_bytes_fully_explained`，如实写明 IDAT 不同、
    chunk 类型一致、像素层面零可视差异。**证据描述必须跟着渲染模型更新。**

八、下一步成本账（B 的 P1/P2）
====================================================================
 A. 贴图 / UV：程序化噪声贴图或 SDXL 出服装纹理再投影。成本中，
    视觉收益中；能显著摆脱「塑料积木」感。
 B. glTF 导出 + Godot 实时 3D 角色：最接近「真 3D 进游戏」，但要动
    Godot 场景树 / 相机 / 动画播放器，且 **ShaderToRGB 是 EEVEE 专有**，
    卡通渲染 shader 必须在 Godot 重写，视觉会先掉一档。成本高。
 C. 渲 228 帧图集 → Godot 2D 精灵：不动现有 2D 判定 / HUD / 状态机，
    但要 alpha 抠底、锚点、图集打包、引擎换帧；建议先渲 8~16 帧
    小样本验证管线，再决定全量。成本中。
 D. 到此为止：作为 3D 设定 / 预览，运行时继续用 A 路线代码自绘appearance-layer。
    成本 0。

 **建议先做 C 的小样本**：它复用已验证的坐标桥与 228 帧表，风险最低，
 且能立刻回答「这套 3D 皮肤到底值不值得渲全量」。在此之前不要渲 228 帧。
