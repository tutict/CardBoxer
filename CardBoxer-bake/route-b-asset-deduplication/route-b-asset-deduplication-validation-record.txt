0. 结论先行
====================================================================

用户反馈的「两个人物重叠在一起」，**不是 GLB 里三套造型叠在同一身体上**，
而是两个 SubViewport 共用同一个 World3D：

  fighter_3d_layer.gd::setup() 里 sv = SubViewport.new() 之后没有设
  own_world_3d，两层 sv.world_3d 都是 null（实测 instance_id=0、
  own_world_3d=false），于是每个视口都把 player 与 foe 两个 GLB 角色
  一起画了进去。两层再各自贴到 2D 左右站位，观感就是「两个人物重叠 /
  一个身体上叠着白衫 + 重甲 + 披风 + 头饰」。

同进程 A/B（boards/B-World3D真因对照.png）：

| 视口 | 现状（共享 World3D） | 各设独立 World3D | 只挂一层的单层真值 |
|---|---|---|---|
| player 近白 / 青 / 占比 | 17,602 / 2,766 / 24.5% | 13,197 / 2,435 / 30.8% | 13,902 / 2,611 / 31.2% |
| foe 近白 / 青 / 占比 | 14,643 / 2,480 / 19.5% | **937 / 412 / 1.3%** | 725 / 424 / 1.0% |

独立后 foe 视口只剩单个纯重甲怪，player 视口只剩单个白长衫少女，
与「一次只挂一层」的单层探针逐项吻合。修复只需在 setup() 里
给 SubViewport 设 own_world_3d=true（或显式分配 World3D），不碰任何资产。

**因此 J / B 路线一直在改 foe-rigged.glb 是方向错误**：删壳删不掉
另一个视口串进来的角色。本轮没有改游戏源码，修复留给工程师确认。

1. 上轮判断为什么错（不粉饰）
====================================================================

上轮依据 `orientation-fix/shots/o-sv-foe.png` 判定「SubViewport 合成前原图
里单个 GLB 就叠了三套造型」，据此建 #165 / B 路线。本轮查到：

* 当前真实路径 `pair-sv-foe.png` 与历史 `o-sv-player.png` sha256
  逐字节相同（f0b0904b…）；`pair-sv-player.png` 与 `o-sv-foe.png`
  逐字节相同（b319cd89…）。
* 这不是「文件标签写反」，而是**图内容由相机 yaw 决定、不由层决定**：
  修朝向前 p=+55 / f=-55，修朝向后 p=-55 / f=+55，于是两层图整体对调。
  共享 World3D 使两个视口看到同一组角色，只是各自用自己的相机看。
* I 路线 v1 早就实测过「改一个 SubViewport 的 DirectionalLight3D 会让
  另一个 SubViewport 的角色一起变暗」（fighter_3d_layer.gd:263 注释），
  当时只当成灯的串扰，没往上追到 world 共享导致几何也串。

2. 三个被证伪的假设（都有落盘数据）
====================================================================

| 假设 | 证据 | 判定 |
|---|---|---|
| 青云纹烘在 B round2 保留壳的 UV 上，几何删壳碰不到 | 纯 GLB 逐面 UV 反查：I 基线 2,809 壳 / 79,998 面；青面 268，**258 面（96.3%）落在被删壳**，保留壳仅 10 面；近白面 0、暖红面 4 | 证伪。B round2 的 UV 特征补删其实打中了 |
| 「删壳没删对 / 目标壳选错」 | GLB 坐标差集独立复核：253 壳 / 10,495 顶点（build_shape_b 报 262 / 10,526，差 9 壳 31 顶点是 glTF 导出按 UV 缝拆点）；4 个长条壳全删；344 个头顶壳删 211 | 证伪。删壳口径本身没问题 |
| 白布只在 -55° 正面视角可见 | 同一 foe 层 +55 / -55 各截一帧：近白 725→668、青 424→449，无数量级变化 | 证伪。相机角度不是原因 |

删壳口径订正过程也留了证：deleted_ratio 是严格双峰（2,556 个壳
精确为 0 = 逐字节未动，253 个壳非零），分界应取「>0」而不是我第一版
写的 0.9；0.9 会把 98 个真实塌缩壳误判为保留，导致「青面 76% 落在
保留壳」的反向错结论。`logs/diag_ratio.out` 是这一步的原始证据。

3. 颜色归因（引擎内 5 状态，同一进程，只改运行时材质/灯）
====================================================================

材质槽位读回：1 mesh / 1 surface / StandardMaterial3D，
metallic=1.0、roughness=1.0，4 盏灯能量 1.9 / 0.75 / 0.55 / 0.95，
albedo = foe 暗灰贴图，emission_texture 空，**没有第二张彩色贴图**。

| 状态 | 近白 | 青 | 亮(>200) | 平均 RGB |
|---|---|---|---|---|
| S0 原样 +55° | 725 | 424 | 1,077 | 52 / 46 / 42 |
| S1 四盏灯能量=0 | 0 | 0 | 0 | 0 / 0 / 0 |
| S2 metallic=0 / roughness=1（贴图保留） | 73 | 250 | 239 | 55 / 48 / 43 |
| S3 albedo 换纯红（金属保留） | 468 | **0** | 26,029 | 166 / 32 / 32 |
| S4 材质还原，只把 yaw 切 -55° | 668 | 449 | 1,436 | 61 / 55 / 52 |

结论：亮/白/青全部来自「四盏高强灯 × metallic=1.0 × albedo」，
与 I 路线 rootcause_i.json 一致；S3 仍有 468 个白像素是镜面高光饱和，
不受 albedo 约束，所以判据写的是「青归零 + 近白下降」而非「近白归零」。

贴图侧交叉验证：foe baseColor（4096²，缩到 1024² 分析）近白 5 px、
青 2,437 px、暖红 62 px；player baseColor 近白占 14.98%。
`j-albedo-foe.png` 是暗灰机械件 UV 岛，`j-albedo-player.png` 才有
大片白长衫 + 靛蓝云纹 + 红花。
