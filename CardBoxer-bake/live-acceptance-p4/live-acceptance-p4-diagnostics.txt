================================================================
日期：2026-11-15
配套：实机验收P4-验证记录.txt（验收与交付）
证据：data/live_p4.json、data/live_p4_analysis.json、

一、要补的到底是什么
----------------------------------------------------------------
P4 静态收口时把话说得很清楚：255 对原生平台里 224 对是整帧定格
hold 帧，落地 micro2 只让数值曲线不再精确相等；引擎内 A/B 是
「同进程冻结静态帧」，**未重跑真实对局通道**。

「实机验收」因此不是再出一张好看的对照图，而是回答三个问题：
  1. P4 落地表在真实自动对局里，引擎真的读到了吗（不是探针注入的）？
  2. 连续节奏里有没有引入可见抖动或卡死？
  3. 改的是 2D 动作表，2D 那一侧在真实画面里还正常吗？

第 3 问是前几轮完全没覆盖的：P1~P4 的引擎内 A/B 全部在
CARD_BOXER_3D=1 下做，而 3D 开态 fighter.gd::_draw() 画完影子就
early return，2D 关节表根本不参与绘制。


二、两个显示状态，两个真相来源
----------------------------------------------------------------
  CARD_BOXER_3D=1（three_d）
    arena.gd 加载 motion_3d / motion_3d_foe（15 卡），
    _sync_3d_layer() 每帧驱动 3D 层；2D 角色只画影子。
    → 验 13 骨 delta、时序、SV 原图、连续节奏。

  默认关（default_off）
    motion_3d 是空字典，_sync_3d_layer() 立刻 return；
    fighter.gd 用 CardMotion.sample() 读 card_motion.json 画 2D 火柴人。
    → 这是 P4 数据层改动的**唯一可见侧**，验整帧画面健康度。

探针按 use_3d 分叉：3D 开态逐行读回 (card, frame) 的 f_knee 表标记
与 13 骨 delta；默认关读回 CardMotion._tracks 的 2D 表标记
（focus:8 的 f_knee）与整帧 PNG。读 mapping 前先判
motion_3d.is_empty()，否则默认关会取到不存在的键。


三、什么不算「实机」
----------------------------------------------------------------
探针里一旦出现下面任一项，这轮就不叫实机，只是又一次注入式 A/B：
  * arena.paused = true（冻结状态机）
  * layer.apply(card, frame)（探针自己驱动动作）
  * motion_3d["mapping"]["leg_cap_deg"] = x（覆盖 mapping）
  * 不 await RenderingServer.frame_post_draw（读到停滞帧缓冲，
    B 路线实测连续采样点 PNG 逐字节相同，GIF 会假卡顿）

这四条写成 verify_live_p4.py 的源码形状判据，且**只扫可执行行**——
注释里出现同样的裸子串不算数（B 路线 verify_live.py 首版就因为
扫全文被注释满足，M06 变异暴露真空通过）。M24~M27 四条变异
逐条证明这些判据有牙。


四、为什么不做跨进程逐帧像素 A/B
----------------------------------------------------------------
B 路线已实测：即使 seed() 固定，跨 Godot 进程整局牌局仍漂移，
三次运行三种牌局指纹。本轮两次真跑终局 HP 是 85:80 与 97:63，
再次印证。逐帧像素等价的前提不成立，硬比只会得到假结论。

替代口径（沿用 B 路线证伪后的做法）：
  取 three_d 真跑读回的 128 个 (card, frame) 序列，
  Python 侧分别按 P4 落地表 / P3 原表复算 13 骨 delta。
帧序列同源，只有动作表不同，逐帧 A/B 才成立。
两次真跑的整帧 PNG 只各自统计「非空、sha 全不同、画面健康」，
不做同一时刻的对照；preconditions 里显式记
framewise_pixel_ab_applicable=False，不折进判据计数。


五、判据口径：先看结果之前钉死
----------------------------------------------------------------
只用两类，避免「挑一个好看的阈值放行」：
  ① 结构性：帧在表范围内、复算覆盖全行、引擎读回 delta 对账、
     站架 delta 全 0、SV 重复图由相同 13 骨 delta 解释、
     阶段时长在规格内（含 hitstop 0.24、第 1 回 discard 排除 intro）。
  ② 可复算上界：D_static = 两版表全量 284 帧上 |P4−P3| 的最大
     逐骨差（1.870037° @wave:34）。实机帧是这 284 帧的子集，
     所以实机最大差必然 ≤ D_static；这是可复算的硬上界，
     不是拍脑袋的放行线。

连续帧跳变首次在 P4 语境量化，**没有历史外部锚**，只报告分布
（max / min / p95 / mean），不设阈值、不拿它当通过或不通过。
「P4 最大跳变不高于 P3」是本轮**实测结论**，不是理论保证，
写在验证记录里、由 60 条判据之一钉住，供以后对比。


六、平台口径别混用
----------------------------------------------------------------
  静态 P4：284 帧**相邻帧**的腿骨 delta 差，精确平台 255 → 0。
  本轮：0.12 s **相邻采样点**（127 对，跨 1~2 帧），
        精确平台 玩家 81 → 72、对手 83 → 74；
        可辨平台（< 0.1°）81 → 81、83 → 83，不变。

可辨平台没降不是失败，而是如实反映 P4 的扰动幅度 ~0.1° 恰好
压在阈值附近，且真实对局只走到部分姿态。两个口径不能互相折算，
更不能拿静态的 255→0 去宣称实机也有同等观感收益。


七、看图证据的边界
----------------------------------------------------------------
三张板全部来自真实对局截帧（整帧 / SubViewport 原图只缩放、不重绘
人物），但：
  * 连续帧条带只有 P4 真跑的图；格子里的 P3 角度是同源复算值，
    不是第二局的截图，板内已写明。
  * 整帧关键帧两行来自两次独立进程，同一 #idx 只是采样序号对齐，
    不代表同一牌局，板内已写明。
  * 双方同卡同帧且两版表 11 关节同步，腿骨 delta 对称相等，
    所以条带板上下两行角度数值相同，板内已写明不是复制粘贴。
  * 差异集中在膝踝，上身与手臂不受影响；肉眼差异很弱。
    结论主要由数值分布与像素差支撑，不夸大成「一眼可见的改善」。


八、零改动证明
----------------------------------------------------------------
本轮不修改任何游戏源码 / 数据 / 资产。唯一写进游戏工程的是把
tests/p4_live_probe.gd 复制过去供 Godot 执行（新增文件，不在受监控
清单内）。run_live_p4.py 在两次真跑前后各算一次 14 个受监控文件的
sha256，写进 data/sha_baseline.json 与 data/live_p4.json 的
sha_before / sha_after，双重留证全同。

因此 P1 / P2 / B / P3 的历史 verify 红因数与 P4 收口时相同，
按项目约定只列债、不篡改历史结论、不放宽阈值、未重跑。
