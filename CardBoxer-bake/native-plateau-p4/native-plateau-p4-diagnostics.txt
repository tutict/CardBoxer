一、为什么要单开这一轮
----------------------------------------------------------------
P3 把硬 clamp 造成的 227 对方波用 atan 软限幅消掉，精确平台从
482 降到 255，并证明「无状态映射已经到理论下限」。剩下的 255 对
不在 retarget 公式里，而在动作表本身。P3 结束时明确留了成本账：
改 card_motion.json 会同时影响 2D 与 3D 双侧逐帧动作，必须先算清
「这 255 对到底是整帧关节重复、局部腿关节重复，还是 retarget 后
腿骨 delta 碰撞」，再决定改哪一层。


二、数据层有两个真相来源
----------------------------------------------------------------
  2D 运行时
    fighter.gd:1027  var baked := Motion.sample(id, phase, progress, f)
    card_motion.gd::_pose_at() 取 11 关节（hip/shoulder/head/
    f_elbow/f_hand/b_elbow/b_hand/f_knee/f_foot/b_knee/b_foot）+ lean
    读 res://data/card_motion.json

  3D 运行时
    rig_driver.gd::_joints_of()
      var raw: Dictionary = motion["cards"][card]["track"][frame]
    读 data/motion_input.json / motion_input_foe.json

改前实测（diag_native.py / probe_layout.py）：
    CM_VS_MI_IDENTICAL            True（三份表 11 关节逐值相同）
    PLAYER_FOE_TRACKS_EQUAL       True
    15 卡 / 284 帧；card_motion.json 另有 motions（3 条受击反应）
因此「只改 3D 表」虽然能让 2D 零变化，却会破坏 P1 的
added_tracks_equal_source_both 与 P2/P3 的 two_card_tables_identical
等跨表对账守卫。本轮选择三表同步改动。

另一个关键事实：3D 开态下 fighter.gd:_draw() 在
`if draw_3d_override: _draw_shadow(...); return` 就早退，2D 关节表
根本不参与绘制。所以「3D 开态做 2D 像素 A/B」前提不成立，2D 侧
改用引擎读回 CardMotion._tracks 量化（p4_2d_readback.gd）。


三、255 对的精确构成
----------------------------------------------------------------
    255 对 = 80 个唯一帧对
      224 对  整帧 11 关节完全相同 —— 定格蓄力 / 保持帧（hold）
       31 对  上身仍在动，但 retarget 后四条腿骨 delta 碰巧同值
    唯一帧对中：56 个整帧相同，24 个上身仍在动

  按卡：wave 43 / focus 28 / hit_heavy 22 / guard 21 / ...
  按骨：thigh_f 73 / thigh_b 63 / shin_f 60 / shin_b 59
  数值微分：1 px 腿关节位移 ≈ 0.8878°；0.1° 可辨差 ≈ 0.1126 px

口径：精确平台 = 相邻输出腿骨 delta 差 < 1e-6°；
      可辨平台 = 差 < 0.1°。全部按 P3 上线态 atan12 复算。

结论先行：**224 对是动画里正常且必要的 hold 帧，不是 bug**。
消除它们不会让画面更好，只会让数值曲线不再出现精确相等。
这一点在落地后看图复核里也得到印证（两版姿态差异肉眼很弱）。


四、候选改法怎么设计的
----------------------------------------------------------------
  MICRO  只在「连续定格段」内给四个腿关节加段内扰动，使相邻帧
         数值必不同；四个关节各给不同单位方向，避免退化成同一条
         骨链的刚性平移。
  LERP   把定格段内各帧从段首线性过渡到「段后第一个不同帧」，
         动作从硬定格变匀速过渡，2D 关节位移大得多，仅作成本对照。
  HYBRID 先 LERP 过渡，再对残留精确平台补 MICRO 0.3。

首版 MICRO 用 `w = A*sin(pi*k/(m+1))`（半周期正弦），m=2 时
k=1 与 k=2 的 sin(60°)==sin(120°)，相邻帧拿到同一偏移，
53 对平台残留（probe_residual.py 实测 RESIDUAL 53）。
改成四分之一正弦 `w = A*sin(pi*k/(2*(m+1)))` 后 k=0..m 落在
[0, pi/2) 严格单调，残留归零。


五、候选扫描结果（evaluate_candidates.py）
----------------------------------------------------------------
    38 个定格段，按 8 档幅度 + LERP + HYBRID 扫描：

    档位                    精确   可辨   改动帧   最大位移
    micro_0（现状）          255    308      0      0.0000 px
    micro_0.05                 0    309     80      0.0490 px
    micro_0.5                  0    257     80      0.4904 px
    micro_1                    0    218     80      0.9808 px

扫描时钉的推荐规则：精确平台归零 + 可辨平台严格低于现状；再按
可辨平台最低、关节位移最小排序 → 自动选出 hybrid_lerp_micro03。


六、落地决策订正：否决自动推荐
----------------------------------------------------------------
扫描规则是纯数学排序，没有把「2D 侧动作语义改写」计入成本。
hybrid 的 33.0606 px 来自 LERP 把整帧定格段改成匀速滑动——这是
重设动画设计，不是修数值平台；且 224 / 255 对本来就是设计意图的
hold 帧。它同时是四档里真实 GLB 撕裂最贵的（0.043500 m）。

最终落地 micro2（幅度上限 2 px，三表同步），并把订正理由写进
data/landing_decision.json，扫描结论原文件不动（不篡改历史证据）。


七、首版落地撞了 pose_probe 红线，已修
----------------------------------------------------------------
四分之一正弦在 k=0 给 w=0、k=m 给 w≈A，正好把位移堆到段末。
wave 的末帧是收招归位帧，被推离站架：

    P3 上线态：表内起收招最大漂移 1.100 px @sweep 末帧（<=1.5）
    micro2 首版：1.569 px @wave 末帧 → pose_probe FAIL，自检 14/15

没有放宽 1.5 px 阈值（那是 pose_probe.gd 的历史承重判据），也没有
简单降幅，而是修扰动形状：
  * 每条 track 的首帧 / 末帧（起手与收招归位帧）刻意不扰动；
  * 段内改 `w = A*(k+1)/(m+2)`，恒 > 0 且严格递增。
    段首也有非零扰动，所以「保护段末」不会让最后一对平台残留。

修后 pose_probe 精确回到 1.100 px @sweep 末帧，自检 15/15。
