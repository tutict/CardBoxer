一、结论（先说结果）
---------------------------------------------------------
造型门槛达成了：生成的是完整、正面、头身比正常、五官可读的二游风 3D 女拳手，
黑白熊猫配色 + 白长外套 + 黑内搭长裤 + 红腰带 + 中国结 + 双环发髻 + 金发夹 +
黑金厚底靴 + 黑拳套，比前几轮程序化几何「积木人 / 纸片人」有质变。

但 C 路线（渲 228 帧动作图集导 2D 精灵）**不具备直接执行条件**，三条硬事实：

  | 事实 | 证据 |
  |---|---|
  | 模型是静态的 | GLB: 0 skins / 0 animations / 1 node；FBX: LimbNode/Deformer/Skin/Skeleton/BindPose/Animation 全 0 |
  | 自动绑骨跑不通 | Blender `ARMATURE_AUTO` 报 `Bone Heat Weighting: failed to find solution for one or more bones`，覆盖率 0/51587 |
  | 根因是拓扑不是姿势 | 861 个互不连通的开放壳体、21580 条非流形边；3 组骨架对照全部 0 覆盖 |

一句话：**模型好看，但它是「一张可以转着看的 3D 立绘」，不是「能打拳的角色资产」。**
这两件事别混。之前程序化几何不好看但能播 228 帧，这个正好反过来。

五、绑骨可行性：失败 → 三次对照 → 根因 → 独立复核
---------------------------------------------------------
5.1 首次 `bpy.ops.object.parent_set(type="ARMATURE_AUTO")`（用 boxer_rig 的 13 骨）：
    日志 `Warning: Bone Heat Weighting: failed to find solution for one or more bones`，
    **0 个有效权重 / 51,587 顶点覆盖率 0.0**。注意 Blender 这次不抛 Python 异常，
    只打 C 层警告并留下 0 个 group —— 用「没报错」判断成功会得出完全相反的结论。

5.2 单变量隔离（probe_rigfit2.py，每次都重新导入 + 归一化，互不污染）：

  | 实验 | 骨架 | 结果 |
  |---|---|---|
  | C1_minimal | 3 根，全在躯干内部 | groups=3，coverage **0.0** |
  | C2_scaled | 游戏 13 骨绕髋缩放 50%，全缩进模型内 | groups=13，coverage **0.0** |
  | C3_apose | 对称 A-pose 13 骨，贴合真实手臂/腿 | groups=13，coverage **0.0** |

    三次全灭 → **与骨骼摆在哪里、是不是格斗站架无关**。C1 只留 3 根躯干骨仍失败，
    排除了「骨骼伸出模型外」这个解释。（Blender 会建出空 group 名，但一个权重都没写。）

5.3 真因 —— 网格拓扑：

  | 项 | 值 |
  |---|---:|
  | 顶点 / 面 / 边 | 51,587 / 79,996 / 130,784 |
  | **非流形边** | **21,580** |
  | 其中边界边 | 21,580（即没有一处封闭）|
  | **连通壳体** | **861** |
  | 最大壳 / top10 | 1,281 / [1281,1106,1102,951,875,735,712,674,615,605] |
  | 孤立顶点 | 0 |

    这是 AI 生成 3D 的典型输出：外套、头发、发髻、拳套、鞋、中国结、脸……
    烘成同一张贴图的**一堆彼此不连、且全部开放的薄壳**，塞进一个 mesh 里。
    Bone heat 依赖封闭体做热扩散，对这种拓扑无解。

5.4 独立复核（verify_shells.py，**完全不经过 Blender**）：
    直接解析 GLB 索引缓冲（239,988 indices / 79,996 triangles）做 union-find，
    得 861 个连通分量、top10 与 bmesh 逐字一致 → `SHELLS_CROSSCHECK_OK`。
    GLB sha256 同时与 probe_report.json 一致（2c85462c…）。
    **两条独立实现算出的数一样，这个承重结论才算数**；单靠 bmesh 一个数不写进结论。


六、兜底路径跑通，但只证明「链路」不证明「质量」
---------------------------------------------------------
绕开 bone heat 的「最近骨骼刚性权重」：每个顶点按到 13 根骨骼线段的最短距离
分配 top-1/top-2 反比权重，手动挂 ARMATURE modifier。

  | 项 | 值 |
  |---|---:|
  | 权重计算耗时 | 0.51 s |
  | 覆盖 | 51,587 / 51,587 = **100%** |
  | vertex groups | 13 |
  | 驱动测试 | `upperarm_f` 旋转 35° |
  | 最大顶点位移 | **0.31552 m** |
  | 平均位移 | 0.00697 m |
  | 位移 >1 cm 的顶点 | 3,430 |

要说清楚：0.3155 m 对 1.72 m 的角色是 **18% 身高**，配合「平均只有 0.007 m」
说明只有一小撮顶点被猛拖走 —— 典型的刚性绑定误分配（远处顶点被判给前臂骨）。
**100% 覆盖 ≠ 变形可用**。这条只能作为「自动化有一条路可试」的下限证据，
没有渲姿势帧、没有目视验证是否撕裂，别当成 C 路线已打通。


七、判据卫生 / 本轮没做的事
---------------------------------------------------------
* 本轮是诊断探针，不是回归守卫：没有写进任何 test suite，也没有变异验证。
  承重数字靠「两条独立实现互证」而非靠断言。
* 「脚本跑完 exit=0」不等于功能成功：bone heat 的失败只体现在 stdout 警告 +
  0 覆盖，判据必须钉**实际写进顶点的权重**，不能钉异常。
* 没做的事（逐条列，不粉饰）：
  - 没渲任何动画帧、没渲 228 帧图集、没做 alpha 抠底/锚点/图集打包；
  - 没试 voxel/quad remesh 封壳后 bone heat 是否成功（这一步只做了诊断，没做修复）；
  - 没验证 glTF 进 Godot、没重写 toon shader、没评估 PBR 贴图在 GL Compatibility 下的表现；
  - 没验证模型朝向在 2D 图集里是否需要绕 Z 旋转（对正面视角直接取 gx→屏幕 x 应该不需要，但未实测）；
  - 没做人形比例的自动判据（头身比 / 肩腰比），造型是否「像正常人」由看图判；
  - 生成模型只是风格参考，未做 IP 合规审查，也未复刻任何现成角色。
* 视觉判读只用 `artifact_02.png` 与 `rigfit_overlay.png`；`ViewImage` 用纯技术性
  query 正常返回，没有出现之前 stance 图那次 `SENSITIVE_CONTENT_UNAVAILABLE`。

我的建议：**先走 C 的 2~8 帧证伪（便宜、直接回答「能不能渲」），同时走 B 出静态
立绘拿到可见收益**；A 等 C 的结果再决定要不要投入。在选定前不要渲 228 帧全量 ——
和前几轮同一个道理：把 861 壳的绑定缺陷固化到 228 帧里，后面抠底/锚点/换帧全部作废。
