二、为什么是 cap=9，不是 12，也不是放开限幅

诊断（diag_p2.py，DIAG_P2_OK 9/9）：15 轨 284 帧、1136 个腿骨帧，
原始 |delta| 均值 10.1991° / p95 34.9608° / 最大 116.0986°。
cap=3 实际只送达均值 2.1599°、峰值 3.0°，702/1136 骨帧被削角。
源数据有动作，瓶颈是硬 clamp，不是动作表没数据。

  cap     送达率    峰值      被削角骨帧
  3°      0.2118    3.0°      702   ← 线上基线
  6°      0.3682    6.0°      526
  9°      0.4901    9.0°      426   ← 本轮选定
  12°     0.5906    12.0°     355
  无上限  1.0000    116.0986° 0     ← 绝不可取，腿会翻折

真实 GLB 成本账（不是历史 C 路线的对手怪高模）：
导入游戏 assets/3d/player-rigged.glb，Blender 5.2.0 LTS headless
逐姿态施加 13 骨 delta，重算 136,092 条边的长度变化。
  player_HI_skinned：57,934 顶点 / 136,092 边 / 79,986 面 / 14 权重组
  e_apose_rig：14 骨（13 链骨 + neutral_bone）
  代表帧 sweep：10 档 × 26 帧 = 260 姿态，max_pose_err 4.77e-07
  全量复核：3 档 × 284 帧 = 852 姿态，max_pose_err 4.17e-07，133.8 s

全量 284 帧结果（analyze_full_tear.py，FULL_TEAR_OK，11/11）：
  cap03_hard_g100  最坏 p999 0.040791 m，>5cm 边 44，越锚帧 0
  cap09_hard_g100  最坏 p999 0.043694 m，>5cm 边 71，越锚帧 0
  cap12_hard_g100  最坏 p999 0.044522 m，>5cm 边 83，越锚帧 0
  最坏帧三档同为 throw/8；代表帧 sweep 的 sampling_gap 全为 0
  ⇒ 26 帧抽样没漏掉更坏的帧，cap9/cap12 全部 284 帧都在锚内

选 9 不选 12 的理由是边际账：12 相对 9 的送达率只多 10 个百分点、
最坏 p999 多 1.9%，但 >5cm 边数从 71 涨到 83，且看图并没有多出
可读性收益。按「最小表现层改动」取 9。手臂增益不动，因为
cap9/gain1.5 的 >5cm 边数会涨到 289，成本明显不划算。

看图复核（boards/ 共 5 张，全部 ViewImage 逐张看过）：
  4 档 A/B 板：站架四档逐像素相同；进攻帧腿部随 cap 逐步打开；
    cap9 已明显可读（玩家 jab 前腿抬起、sweep 两腿分开；对手 jab 抬腿）；
    cap12 无甩飞 / 穿模 / 出框但增益边际变小。
  上线前后板：两列（运行时回滚 cap3 / 引擎读回落盘 cap9），
    文字无截断、无重叠、无缺字方框，差异可辨。
  增益撕裂权衡板：补了右轴 x0..x4 刻度与双轴说明，量纲无歧义。
