一、结论先给

P2 真正可攻的缺口是「腿」，不是「双臂」；而且腿的问题是**硬 clamp
把源信号削掉约 79%**，不是源数据没动作。

  腿部原始 |delta|（1136 个骨帧）  均值 10.1991° / p95 34.9608° / max 116.0986°
  leg_cap=3° 实际送达              均值 2.1599° / max 3.0°
  信号送达率                        21.18%（78.82% 被削掉）
  被削角的骨帧                      702 / 1136（61.8%）
  被削角的帧（至少一根腿骨）        见 per_track，几乎所有轨道都中

  候选 cap      送达率     峰值      仍被削角的骨帧
  3°（当前）    0.2118    3.0°      702
  6°            0.3682    6.0°      526
  9°            0.4901    9.0°      426
  12°           0.5906    12.0°     355
  无上限        1.0000    116.0986° 0  ← 绝不可取

原始腿部最大值 116.0986° 是 2D 侧视关节角映射到正面 A-pose 骨架时
的极端值（膝盖/脚坐标越过髋部参考轴，角度接近翻折），直接放开 cap 会把
腿甩到不可读的姿态。所以「放开限幅」必须同时解决**长尾**：要么保留
有界 cap 并接受平台期，要么改成有界软压缩（tanh 一类），不能裸 clamp。

────────────────────────────────────────────────────────
二、订正上一轮我自己的说法（重要）

上轮收口时我写「两条手臂仍不会在同一招里同时大幅动」，把「双臂」列成
P2 缺口之一。**实测不成立**：

  15 轨中双臂峰值都 >= 8° 的轨道（5 条）
      focus / hit_heavy / sweep / throw / wave
  双手信号同时触发的帧                 66 帧
  单臂冻结（另一臂峰值 < 2°）的轨道（5 条）
      jab / cross / uppercut / backstep / sidestep

后 5 条是 2D 格斗的招式语义本身：jab 出前手、cross 出后手、uppercut
抬前身、backstep / sidestep 靠重心与腿。把 jab 硬凑成双手齐动会违反动作
语义、等于自造动作（P1 已明确不自造 hit_crush，同理不自造双臂）。
因此 P2 **不改双臂语义**，只把这条订正写进结论，避免后续按错误前提动刀。

四、历史撕裂成本的适用性边界

  puppet_mapping.json 与当前游戏 motion_input.json 的 mapping 数值逐项相同
  （mapping_equal=True），x1.5 手臂增益对应峰值 42.0° 也与旧 sweep 的
  max_delta_deg=42.0 吻合 ⇒ retarget 公式链同口径。

  历史 C 路线 gain_sweep.json（对手怪 V1 高模 / 3 卡各 1 帧 /
  Blender CPU evaluated mesh）：
    刚性权重基线 p999      0.28048 m
    x1.5 arm_only 三卡     0.02808 / 0.05411 / 0.02749 m
    全部 7 档最坏 p999     0.09365 m（= 刚性基线 33.4%）
    看图可用区间           1.0 .. 1.5（2.0 勉强，3.0 不可用）

  但当前游戏是 player-rigged.glb / foe-rigged.glb 的 GPU skin、
  15 卡 284 帧，网格与帧集都不同。**旧数字只能当方向性锚，不能当放行
  上限**；P2 阶段二必须在游戏真实 GLB 上重测增益-撕裂曲线。

六、P2 落地后的实测订正（2026-11-14，保留原文，只追加）

  1. 上面「已知会红的历史守卫」**少列了一条**。实际运行
     verify_motion_p1.py 得到 50/52 FAILED，红因恰好两条：
       mapping_gains_unchanged_both
       non_cards_fields_equal_backup_both
     后者断言「除 cards 外的所有字段与 P1 备份逐值相等」，而
     mapping 正属于「非 cards 字段」，P2 改 leg_cap_deg 必然红。
     其余 50 条仍全绿。P2 的 verify_p2.py 已把「恰好两条预期红因 +
     其余 50 条绿」钉成判据，不篡改 P1 历史结论。
  2. 上面 §五 第 1 步写「Blender 5.2.3 headless」，实测探针用的是
     系统 **Blender 5.2.0 LTS**（hash fbe6228777e7...），见
     data/tear_sweep_blender.json 与 data/full_tear_blender.json 的
     blender 字段。便携 5.2.3 是另一份安装，本轮没用。
  3. 最终选定 cap=9（leg_cap_deg 3.0 → 9.0），不是 12、也不是软压缩；
     依据是全量 284 帧真实 GLB 复核 + 引擎内 A/B 看图，详见
     动作表现P2-验证记录.txt。
