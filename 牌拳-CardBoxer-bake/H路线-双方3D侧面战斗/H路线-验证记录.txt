3. 为什么对手怪必须单独一份动作输入
====================================================================

probe_blends_h.py 读回两份 .blend：骨名 13 根完全相同、骨架对象变换
相同，但 rest 矩阵不同（FACT rest_matrix_identical=False）。
rig_driver.gd 的 setup() 从 Godot Skeleton3D 读 global_rest，并用
motion_input.json 的 apose_points 作旋转中心；若把玩家那份 apose_points
喂给对手怪，等于用别人的关节位置算角度，动作会整体错位。
diag_rest_h.py 逐骨列出 dhead / dmatrix；make_foe_motion_h.py 按
Blender bone.head_local/tail_local 的 (x, z) 重建对手 rest，并先拿玩家
那套公式反算一遍 F 路线的 apose_points 验证口径（最坏 1e-6），再替换。

4. 判据订正：CROSS_H_SUSPICIOUS 不是 bug
====================================================================

第一版 diag_cross_h.py 拿「双侧截帧」与「两次单侧隔离截帧」做跨进程
ROI 绝对像素等价，要求对应侧 ratio < 0.20，实测四个 ratio 全在
0.4093~0.5409，报 CROSS_H_SUSPICIOUS。

这是口径错，不是串味：三张图来自三个不同的 Godot 进程，每次启动
随机化全局 RNG，观众席 / 灯光相位 / 手牌都变。G 路线已经把「跨进程
整帧像素等价」退役过一次，H 第一版等于把退役结论又捡回来用。

订正（diag_cross_h.py v2，v1 负结果原样保存在
data/cross_h_v1_retired.json，ok=false 保留）：
1. 四个 ratio 只作事实记录，不再要求绝对值。
2. 改方向性判据：双侧左侧更接近 only=player（0.4239 < 0.5409，
   余量 0.1170），双侧右侧更接近 only=foe（0.4093 < 0.5280，
   余量 0.1187），余量 > 0.05 不算噪声抖动。
3. 真正的主证据换成同进程同树的 data/vp_diag_h.json：
   player-hidden 时右 ROI 0/33920 不变、左 ROI 0.4499 变化；
   foe-hidden 时左 ROI 0/33390 不变、右 ROI 0.4297 变化。
4. verify_h.py 用 H45/H48/H49 三条钉住：退役指标必须点名、
   旧 left_ok/right_ok 绝对阈值字段必须消失、v1 负结果不许被当成 PASS 复用。

5. 视觉诊断：两个角色像不像（不靠肉眼下结论）
====================================================================

h-both-stance.png 里左右两个角色看起来几乎是一个模型镜像，必须排除
「两个层其实加载了同一份 GLB / 串了同一张贴图」。diag_identity_h.py
给三条可复算证据：

| 证据 | 数值 | 判定 |
|---|---|---|
| 两份 baseColor 64×64 缩略图 MAE | 75.3802 | 不是同一张贴图 |
| baseColor 平均 RGB | 玩家 [110.06, 103.65, 95.55] / 对手 [33.21, 32.26, 31.43] | 亮度差 3.3 倍 |
| 同进程单角色 ROI 水平镜像后差异率 | 0.8667（MAE 35.5448） | 只证明两帧非同一张图；ROI 含背景，不作角色差异证据 |
| 同进程两侧 ROI 平均亮度 | 玩家 80.19 / 对手 89.46（差 9.27） | 渲染输出确实不同 |
| GLB 顶点数 / X 跨度 | 57,934 / 1.254475 vs 64,059 / 1.216869 | 几何不同 |

第一版把「镜像 ROI 差异率」当成「角色长得不同」的证据，是夸大：
ROI 里包含擂台绳索 / 观众席 / 灯光，水平镜像后背景必然错位。
订正后该判据改名 frames_not_identical_including_background，输出加
roi_scope_note；真正针对渲染的证据换成两侧 ROI 平均亮度；结构层靠
GLB 顶点数、bbox、三张 PBR sha256，以及引擎内读回的 mesh_sig /
SubViewport / ViewportTexture 各自独立。verify_h.py H25 会检查
scope_note 存在，防止哪天又把这条判据夸大复用。

结论：不是串味，是**造型语言同源**。两份资产的底色亮度、几何、贴图、
渲染亮度都不同，但轮廓、披风、下摆、头饰过于接近，视觉区分度仍不合格。
造型区分度本身是看图判断，不用像素指标硬撑；这是造型层待办，
不进本轮「接线是否成立」的判定。

8. 踩坑（本轮新增，可复用）
====================================================================

1. **退役过的判据会被下一轮原样捡回来**：G 路线已退役「跨进程整帧
   像素等价」，H 第一版又用它当双侧串味判据。修法不是放宽阈值，
   是把口径换成同进程同树 A/B，并把 v1 的 ok=false 当作必须保留的
   负结果证据，再写三条守卫钉住不许复用。
2. **同骨名 ≠ 同 rest**：骨名、数量、骨架对象变换全一致时，
   rest 矩阵仍可差 0.63 m。凡是「复用驱动表」的场合，必须先读回
   bone.head_local/tail_local 逐骨比，不能只看骨名集合。
3. **两张贴图 sha 不同 ≠ 画面看起来不同**：肉眼判「同一模型」不可靠，
   要同时给缩略图 MAE、平均 RGB、两侧 ROI 平均亮度、几何顶点数，
   才能把「串味 bug」与「造型雷同」分开。而且 ROI 含背景，
   镜像差异率只能证明两帧非同一张图，不能证明角色长得不同——
   第一版就在这里夸大了，第二版改名 + scope_note 订正。
4. 双 SubViewport 的 prims 不是可加量，双侧 1,104,816 ≠ 118,856 +
   242,722；别拿帧统计当「两层都渲染了」的证据，用同进程隐藏 A/B。

9. 边界（明说没做的）
====================================================================

- GLB `0 animations`：动作全靠 GDScript 每帧现算 13 骨 pose，
  不是引擎内动画资源；仍是 73 帧三档（stance/jab/cross/wave），
  不是全 228 帧；没有受击 / 输家 / 平局轨道。
- 视觉区分度不合格（第 5 节）；没重做对手怪造型、没调材质亮度、
  没统一两人的构图与大小（DRAW_SCALE 仍是 0.45）。
- 没测 3D 开时的 perf_probe 帧统计 / GPU skin 成本；双侧 prims
  口径异常未解释。
- 默认关：不设 CARD_BOXER_3D 看到的仍是原来的 2D 游戏；
  view_flip 有开关但默认 false，没按 facing 自动镜像，玩法层朝向没动。
- 产物是 Godot 工程内的运行时接线，不是导出的可执行包；
  没导 glTF 反向回 Blender，没做真机 / 移动端验证。
