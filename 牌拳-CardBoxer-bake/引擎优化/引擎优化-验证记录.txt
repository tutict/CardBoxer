========================================================================
二、根因：为什么那一段是死绘制
========================================================================
arena.gd::_draw_backdrop() 原本每帧先画：
  6 条夜空色带 + 2 个月亮圆 + 远景楼群 + 近景楼群 + 46 盏闪烁灯窗
  （灯窗还带 sin(_time * 1.7 + ...) 的逐帧计算）
然后立刻：
  draw_texture_rect(BackdropTexture, Rect2(-40, -40, 1360, 800), false)
  draw_rect(..., Color(0.055, 0.045, 0.085, 0.20))
源码注释自己就写了「图像背景盖掉上面那套程序化色带/剪影」。

  * background/arena.png = RGB，无 alpha 通道（判据 V04 从盘上读）
  * 贴图矩形 [-40,1320] x [-40,760] 完整包含 1280x720 视口（判据 V05
    从源码正则提 Rect2 参数后独立计算）
  * 楼群 x 上界虽到 1340，但超出视口 [0,1280] 的部分本就不可见
=> 视口内那整段绘制 100% 被覆盖，删掉不改变任何像素。

同时删掉 _build_backdrop()（生成楼群缓存）与 _background_cache 字段：
它们只在被删的绘制里被读，留着就是死数据。

保留：贴图 + 暗罩 + 2 个光锥 + 地面 + 9 条横向地板线 +
13 条透视地板线 + 2 根边界柱 + 2 处脚下反光（这些在贴图之后画）。

========================================================================
三、A/B 是怎么测的
========================================================================
tests/perf_probe.gd（真实 GL 窗口，不能 --headless）：
  实例化 main.tscn -> paused=true -> 隐藏所有动态子节点。
  arena._process 只走 paused 分支（queue_redraw + return），_shake 恒 0，
  _shake_offset() 恒 ZERO，因此每帧像素完全确定。
  采 120 帧 Performance.TIME_PROCESS / RENDER_TOTAL_PRIMITIVES_IN_FRAME /
  RENDER_TOTAL_DRAW_CALLS_IN_FRAME，并截一张纯背景 PNG。

  优化前：primitives 482、draw_calls 13、process 4.271ms，120 帧全部恒定
  优化后：primitives 188、draw_calls  9、process 2.605ms，120 帧全部恒定
  两张 PNG 都是 660210 B，逐像素 changed=0、diff extrema ((0,0),(0,0),(0,0))。

改完 project.godot 后复跑 after 探针：primitives 188 / draw_calls 9 /
像素仍逐字节相同 —— 窗口 override 不影响 1280x720 渲染通道。

========================================================================
四、判据设计错误与订正（本轮最值钱的负结果）
========================================================================
初版想用「优化后重渲 8 张注入态节奏帧 vs 上轮归档逐像素 identical」
当视觉回归证据，结果 0/8 全红、每张差约 60 万像素。

看图定位：两张 t048 帧的 HUD / 角色 / 背景几乎一样，**手牌不同**
（新帧 刺拳/刺拳/格挡/投技/交叉反击；旧帧 蓄势/刺拳/上勾拳/刺拳/交叉反击）。

先怀疑「删 _build_backdrop() 少构造一个 RandomNumberGenerator，
导致全局随机序列偏移」—— 写 tests/rng_probe.gd 实测推翻：
  new_consumes_global=false（构造 RNG 不消耗全局序列）
  a=b=c=0.349460930（显式 seed 后完全可复现）
  但**不调 seed() 时，三次独立运行 unseeded = 0.206 / 0.453 / 0.131**
=> Godot 每次启动随机化全局 RNG；发牌用的 randf() 每次运行都不同。
   跨运行逐像素复现本来就不成立，与优化无关，是判据设计错了。

订正：退役「8 张全图逐像素 identical」判据，改为
  compare_regression.py: 只验 8 张帧正常生成 / 尺寸 / 引擎无错误 /
                        arena.gd 逐字节还原 / 静态 A/B changed=0，
                        全图差异如实写进 JSON 但明确标注 informational。
  零视觉变化的硬证据 = 同状态静态背景 A/B（同一棵树、同一冻结状态、
  只差优化），不是跨运行游戏帧。
  RESULT: REGRESSION_EVIDENCE_OK

另一条判据订正：engine_opt_check.gd 初版用全文件 `range(9) == 1`，
但 arena.gd 里第 996 行还有另一个 range(9) 循环，35 条里红了 1 条。
改成只钉 _draw_backdrop() 函数体内的地板线（切片 + count），37/37 全绿。

窗口探针订正：初版读 get_viewport().size 得 1600x900 就判失败；
stretch 下那是物理渲染尺寸，逻辑画布要读 get_visible_rect().size。
改后 physical=1600x900 / logical=1280x720 / scale=1.25，6/6 通过。

========================================================================
五、屏幕放大的做法（为什么不改任何游戏代码）
========================================================================
project.godot 原本已是 stretch/mode="canvas_items" + aspect="keep"。
只加两行：
  window/size/window_width_override=1600
  window/size/window_height_override=900
逻辑画布仍是 1280x720 —— 血条、手牌、角色站位、背景 Rect2 等所有
硬编码坐标一律不动，由 Godot 等比放大 1.25 倍。1600x900 与 1280x720
同为 16:9，无黑边无拉伸。想再大改成 1920x1080（1.5x）即可，仍是两行。

大窗口完整游戏帧 大窗口截图/节奏帧-t048-命中HIT.png = 1600x900，
看图确认 HUD / 五张手牌 / 两名角色 / 擂台背景全部完整、无裁切、无错位。

========================================================================
七、边界 / 没做的事
========================================================================
* 这是「删死绘制 + 窗口等比放大」，没有做按需重绘 / 静态层一次性提交 /
  静态背景预合成纹理等更激进的改造。
* process_ms 是真实窗口下 Performance.TIME_PROCESS 采样，不是纯 CPU
  微基准；绝对数值受机器与驱动影响，看的是同机 A/B 差值。
* 8 张回归帧跨运行不可逐像素复现（全局 RNG 每次启动随机化），已在
  第四节如实说明并退役该判据。
* window_probe_result.json 是探针归档快照；改 project.godot 后必须
  重跑 run_window_probe.py 才会更新，判据不自动重跑探针。
* 侧身 3D 人物仍未接进游戏（见第九节），本轮没有替换角色渲染。
* 20 条判据只钉可复算事实，不评造型、不评手感、不评好看。

九、关联问题：侧身 3D 人物为什么没放上去

  * 所有生成模型（V4b 玩家 / 对手怪 / V1-V3）都是静态 A-pose、

    产物是 PNG 序列，不是可驱动的 3D 模型；从没进过 Godot。
  * B 路线只把 KOF 命中节奏搬进 resolve，明确没搬资产；
    C 路线修好了真 3D 撕裂（p999 0.28048 -> 0.01806 m），
    但动作幅度仍偏小，且没有导出逐帧动作资产。
  * 游戏内角色仍是 fighter.gd 的 2D 代码自绘 + 228 帧 baked2.json
    关节表，判定与动画全靠它；直接换成静态 A-pose 立绘会推翻
    动作表与 12 套自检。

要放上去有三条路，成本差别很大（等工程师定）：
  A 把已渲好的 55 度侧身 PNG 序列做成 2D 精灵，替换 fighter.gd 自绘

  B 用 C 路线的连续壳 + 平滑权重烘 228 帧小样本图集再接精灵
    —— 天级，但动作幅度要先调到位。
  C 真 3D 模型进 Godot（glTF + 骨架）—— 会推翻 2D 判定与坐标桥，
