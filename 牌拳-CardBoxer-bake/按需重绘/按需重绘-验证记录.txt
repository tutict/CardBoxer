========================================================================
二、根因与做法
========================================================================
静止帧仍在每帧重发绘制命令，源头是 4 个 CanvasItem 各自无条件
queue_redraw()：arena.gd 三个分支、hud.gd::_process 末尾、
fighter.gd::tick 末尾（×2 人）、fx_layer 由 arena 驱动。
诊断明细与成本账见 静止帧诊断.txt。

做法：**绘制输入快照**。每层把 _draw() 会读的全部状态串成一个键，
与上一帧比对，键变才 queue_redraw()。
  * arena + fx_layer 共用一个键（_arena_visual_key）：_flash、双方
    position.x、world/fx_layer.position、effects、projectiles、
    tk_rhythm_t/winner/hit、输家位置与 visual_shift、双方 visual_shift。
  * hud 用自己的键（_visual_key）：36 个 arena.<field>、双方 hp/meter/
    display_name、_hp_shown，以及**只在真有脉冲动画时才进键的 _time**。
  * fighter.gd 不接门控：_breath 每帧 +delta，签名每帧都变，接了零收益，
    还会碰 12 套动作自检对 tick() 的依赖。

四条安全边界：
  ① 第一帧强制重画（_force_redraw 初值 true + 空串哨兵）；
  ② 震屏 _shake>0.05 时逐帧重画（_shake_offset 用 randf_range，缓存命令
     会与新的 world.position 不一致）；
  ③ HUD 脉冲条件（任一方 hp_ratio<0.3 / 任一方怒火满槽）成立时把 _time
     放进键，等价于强制逐帧重画；
  ④ 树未建完（自检脚本在 _initialize() 里 add_child 不触发 _ready）返回
     "init"，不访问 Nil 字段。

外部注入式截帧脚本直接改 arena 字段时不需要配合调 API：键下一帧自然变。
另给 force_redraw() 公共入口，但本轮没有任何生产路径依赖它。

三、像素等价（同一进程、同一棵注入态的树，只切 gate）
========================================================================
tests/redraw_probe.gd 把 hand / hp / tk_* / rage / banner / effects /
projectiles / shake / rhythm 全部写死，arena.paused=true 让 fighters 不
tick（呼吸也停），再分五段相位切换 arena.redraw_gate_enabled：

  相位           gate    PNG                    用途
  off            false   A_静止-关闭.png        基线
  on             true    B_静止-开启.png        静止帧等价
  changed_on     true    C_变更-开启.png        换一张手牌后仍要刷新
  changed_off    false   D_变更-关闭.png        同状态基线
  back_on        true    E_回退-开启.png        改回去也不能残留旧帧

  A vs B        changed_px = 0      （两文件均 498219 B）
  C vs D        changed_px = 0      （两文件均 499952 B）
  E vs A        changed_px = 0
  A vs C        changed_px = 3504   bbox (250,568)-(401,684) —— 正是
                第 1 张手牌，证明「状态变化看得见」，不是停更

同进程是关键：Godot 每次启动随机化全局 RNG，跨运行手牌不同；上一轮
引擎优化/ 已因这个坑退役过一条逐像素判据。

绘制调用账（redraw_stats 逐层计数，Time.get_ticks_usec() 实测）：
  相位           draws   draw_us   分层
  off            270     27946     arena 3594 / fx 206 / hud 24146
  on               0         0     skips=270
  changed_on       1       760     只 hud 画一次
  changed_off    210     20051     逐帧刷
  back_on          1       393     只 hud 画一次
=> 静止 90 帧省 27946 us（约 310 us/帧），其中 86% 是 HUD 的 5 张卡牌
   与多段 draw_string。状态变化只花 1 次 HUD 重画，没有多刷。

========================================================================
四、性能 A/B（三组独立进程，冻结背景探针）
========================================================================
tests/redraw_perf_probe.gd 与 引擎优化/perf_probe.gd 同口径（paused +
隐藏动态子节点 + 120 帧采样），在采样窗口开始处清零统计，排除首帧字体
/贴图预热：

  pair   gate0 proc_ms  gate0 draws/draw_us   gate1 proc_ms  gate1 draws/draw_us  像素差
  1      4.0129         121 / 4870 us        2.6710         0 / 0 us            0
  2      2.7920         121 / 5143 us        2.5250         0 / 0 us            0
  3      2.6010         121 / 4931 us        2.6200         0 / 0 us            0
  均值                   121 / 4981.3 us                    0 / 0 us

  draw_us 4981.3 -> 0（-100%）；skips 360/组；
  prims 188.00 / draw_calls 9.00 在 gate0 与 gate1 **完全相同**。

最后一项是本轮最有用的物理解释：跳过 queue_redraw() 并不会让
RenderingServer 少画图元 —— 上一次 _draw() 提交的绘制命令被保留并继续
合成，所以像素不变、图元数不变；省下的是**脚本侧每帧重新发出命令的
工作**。这也是为什么 CPU 证据必须用 _draw() 内的微秒计时，而不是图元数。

**TIME_PROCESS 已被本轮退役为收益判据**：连续两次 A/B 出现过
gate0=4.041/gate1=2.597 与 gate0=2.642/gate1=4.039 的整体翻转；三组样本
off=[2.594,2.984,2.659]、on=[2.526,2.634,4.144] 明显双峰、随窗口节流漂移。
它只作为「窗口采样，不是 CPU 微基准」的负结果记录，不写进任何收益结论。

键的开销用 tests/key_bench.gd 实测（20000 次）：
  str()  5.9862 us/次，hash() 0.1179 us/次，比值 50.8。
本轮**保留 str()**：逐字串比较没有哈希碰撞，代价约 2 个键 × 6 us =
12 us/帧，只占静止帧省下的 ~310 us/帧 的 4%。这是明确的取舍，不是没测。

========================================================================
六、负结果与判据订正（本轮踩到的四条）
========================================================================
① SceneTree._initialize() 里 add_child 不会触发 _ready()：首版
   redraw_gate_check.gd 直接读 world / fx_layer / hud 报 Nil，脚本崩在
   _initialize、Godot 没有 quit 而挂住。修法：arena/hud 的键加「树未建完」
   早退，自检里显式 a._ready()（与 taikou_flow_check.gd 同法）。
② TIME_PROCESS 双峰、跨运行翻转 —— 已退役，改用 _draw() 内微秒账。
③ 跨运行节奏帧逐像素判据不成立：8 张全部 changed≈60 万像素，振幅以
   ±0..6（另有一簇 ~13）的背景重采样低振幅大面积偏移为主，叠加角色呼吸
   相位与随机手牌的高振幅局部差异。见 节奏回归诊断.json，
   verdict=CRITERION_RETIRED；兼容性改由同进程 A/B + 8/8 截帧成功承担。
④ project.godot 现在有 1600x900 window override，capture_rhythm.py 不带
   --resolution，出的 PNG 是 1600x900，与 引擎优化/回归帧/ 的 1280x720
   基线尺寸不符。写 capture_rhythm_1280.py 只给命令补 --resolution，
   注入逻辑不复制、不过期。
⑤ 隐藏的 CanvasItem 被 queue_redraw() 时仍会跑 _draw()（冻结探针里
   arena 画了 121 次，fx/hud 没画）——所以「隐藏就免费」是想当然。

========================================================================
七、边界（不承诺的事）
========================================================================
* 不承诺 live 战斗动作期间省 CPU：fighter.gd 仍逐帧重画，呼吸本来就在变。
* 不承诺整体 FPS 提升百分比：没有可用的稳定 CPU 微基准；只给出被跳过的
  _draw() 调用数与实测微秒。
* 不改判定、不改动作表、不改节奏数值；HIT! 定格、注入截帧、暂停态全部
  保持原样。
* 门控是逐层的，不是整棵树一次性冻结；任一层键变只刷那一层（arena 与
  fx_layer 共键会一起刷，多余的这次刷新不影响像素）。
* 上游若再往 hud.gd 的 _draw* 里读新的 arena.<field>，V10 与
  REDRAW GATE CHECK 的「每个 arena.<field> 都必须在快照里」会报红，
  必须同步补进 _visual_key()。这是刻意留的承重针脚。
