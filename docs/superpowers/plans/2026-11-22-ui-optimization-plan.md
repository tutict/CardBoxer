# CardBoxer 界面优化方案

日期：2026-11-22。状态：A–D 已实施；最终验收见 [实施记录](../../ui/2026-11-22-ui-implementation.md)。本文件保留初始方向和仍待验证的边界。

推荐方向是保留现有深色、低饱和的格斗界面，让玩家依次看懂“对手这一拍做什么、我的牌能否够到、预估是否确定、执行后为什么命中或失败”。先解决读牌，再收紧布局，最后统一天赋与反馈的表现。

参考与当前截图见 [调研记录](../../ui/2026-11-22-ui-reference-research.md)。布局示意见 [1600×900 示意图](../../ui/2026-11-22-ui-layout.png)，它是规划图，不是已实现的运行截图。

## 1. 目标与已有约束

主要使用者是在桌面上用鼠标或数字键读牌、安排五拍攻防的玩家。编排阶段以完成决策为主，结算阶段让角色动作与结果对应。

沿用已有决定：

- Godot 4.5、GDScript、双方原生 3D 模型及现有擂台；默认最大化、1600×900 逻辑画布。
- 五张动作牌一次按顺序编排；两行五拍同页可见，卡槽保持 54px 高。
- 默认八张、最多十张手牌；不增加先弃牌或二次确认阶段；每轮最多三次换牌。
- 敌方先锁定，编排时实际明三暗二，玩家确认时揭晓；编辑计划不会改变敌方承诺。
- 六选三天赋、按所选顺序触发；现有牌型、帧数、伤害、连段和 AI 合约作为既定输入。
- 保持大手牌、简短牌面、完整悬停详情；颜色用于辅助识别。

方案用于指导获批的 UI 实施。保留 Godot 4.5、原生 3D 擂台、五拍和十张手牌等既有约束。实施截图与验收结果见 [实施记录](../../ui/2026-11-22-ui-implementation.md)。

## 2. 方向比较

| 方向 | 具体结构 | 取舍 |
|---|---|---|
| A：克制的格斗 HUD + 五拍对位（推荐） | 顶部稳定状态条，双方同列对照，中央擂台，底部大手牌与开打 | 最贴合此前试玩要求；主要复用现有 HUD 和公开数据 |
| B：牌桌为中心 | 天赋与牌型聚拢在侧栏，编排和手牌占据中央 | 构筑感更强，但会缩小擂台、改变既有空间分配 |
| C：电影式格斗 | 擂台和角色占据绝大部分画面，卡牌随阶段展开 | 演出更突出，但十张手牌和双方五拍难以始终同页可见 |

方案按 A 展开。它是本次调研后的推荐，不是用户已批准的新视觉风格。

## 3. 信息层级与布局

### 推荐的逻辑坐标

| 区域 | 建议坐标或范围 | 内容与要求 |
|---|---|---|
| 比赛状态 | y=0–136 | 双方头像、血条、怒火、中央局数/比分/轮数、三项天赋；暂停和重开保留弱强调的可点击按钮 |
| 我方计划 | 行标题在 y≈162，卡槽 y=180–234 | 五个槽宽约 293px，x 从 48 开始，间隔 10；距离信息放在行标题 |
| 敌方计划 | 行标题在 y≈250，卡槽 y=264–318 | 与我方逐列对齐；明三暗二；不为暗牌显示类别、牌点或射程 |
| 擂台 | y=318–656 | 相比当前计划区终点 y=366，增加约 48px 可见空间；人物、镜头和动作沿用现有实现 |
| 操作条 | y=656–700 | 手牌数量、已选数量、上轮回顾、剩余换牌次数、撤回与开打；按钮 y=660、h=40 |
| 手牌 | 正常 y=708–880；选中 y=700–872 | 保持当前 172px 高、宽度上限 180px；8 张约 177.5px、10 张约 139.6px；选中抬升 8px，不能与操作按钮重叠 |
| 快捷键与牌堆 | y=880–900 | 统一提示数字键、拖动、Shift+数字、Backspace、空格、P/R；不把按键说明重复铺满牌面 |

坐标是实施起点，允许为真实字形和长文做小幅校正；54px 卡槽、完整十张手牌、等价输入与单页编排是验收约束。第一阶段可保留现有位置，第二阶段再统一迁移这些坐标与命中区域。

同一拍的上下卡槽共享视觉关联：悬停任一槽时轻描同列另一槽；当前执行拍沿用双方同步高亮。每槽保留拍号，使任一行都能独立定位。

### 牌面的分工

- **手牌**：连段角色小标、牌点、醒目的招式名、一行起手/伤害、带文字的射程三格。选中后小标位置改为编排拍号，角色仍可从详情查看。
- **计划槽**：拍号、招式名、短预估/结果标签；第二行固定显示起手/伤害与紧凑射程。牌点和连段角色留在手牌及详情，减少重复。
- **详情**：完整效果、连段角色、起手/收招/打空恢复、打断与抗断、预估伤害范围及说明。将“连段起始”与“起手帧数”分开命名；不改变它们的规则含义。

计划槽不再把预估直接拼进数值字符串。预估/结果占用固定标签区，完整参数留在详情；布局必须先为文字分配空间，再安排图标与边框。

## 4. 关键组件与状态

### 4.1 字体、配色与控件

继续使用有完整中文字形的无衬线字体。建议逻辑字号从以下范围试排：招式名 20–22，计划与手牌关键数值 17–18，结果/原因 18–22，说明与快捷键 16–18。最终用 1080p 截图量字形主体高度，重要文字以至少 18px 为目标，不将 Godot 的字号参数直接等同于实测高度。

保留当前深色底与低饱和攻击/防御/位移/调整分类色。主文字使用亮色；金色集中在开打、选中、当前拍和天赋触发。暂停、重开与常规换牌使用中性色边框，悬停和焦点清楚可见。禁用按钮同时给出状态词或说明，不只变灰。

换牌按钮可用单字“换”，或矢量箭头配可读提示；避免依赖系统字体可能缺失的特殊 Unicode 字形。示意图采用单字按钮。

实施时以 XAG 102 的常规重要文字 4.5:1、禁用文字 3:1 为检查目标。高对比模式、200% 文字缩放和屏幕朗读属于后续扩展，不作为这轮已完成或完全符合 XAG 的声明。

### 4.2 射程

用“贴 / 中 / 远”三格表示可达范围，覆盖格带实底或下划线，文字始终可读；悬停显示完整“贴身–中距”等目录文字。距离标题显示当前公开距离。

这是卡牌射程信息，不是“未来必定命中”的保证。移动会改变后续距离，不能只依据编排开始时的距离禁用攻击牌或直接标成打空。完整计划的风险继续从公开预测得到。

### 4.3 预估与真实结果

| 状态 | 显示 | 数据边界 |
|---|---|---|
| 选了 0–4 张 | 槽位与招式信息；不显示结果承诺 | 沿用当前部分计划不预测的规则 |
| 完整计划、预测等待 | 小型“预估中”标签 | 不保留上一份旧预估 |
| ready 且结果类别一致 | 实线标签，例如“预估·可确反” | `certain` 只说明合法公开补全的结果类别一致；伤害仍可有范围 |
| ready 且结果类别不一致 | 点线标签，例如“预估·结果未定”或“预估·距离风险” | 详情解释“受暗牌或前拍影响”，显示聚合范围 |
| error | 一处“预估暂不可用”，槽位保持无预估状态 | 仍可正常开打；不伪造成功标签 |
| 已接触或动作已完成 | 标签改为真实“命中 / 被格挡 / 打空 / 被打断 / 完成”等 | 只读取已执行反馈，未来拍保持无结果 |

预测保持后台单任务、版本丢弃、公开快照与有限缓存。HUD 消费 `forecast_status`、`forecast_certain`、各拍聚合与反馈；不读取真实暗牌，也不输出命中百分比、暗牌候选列表或暗牌身份。

### 4.4 结果解释与上轮回顾

当前已存在命中和失败原因；本轮要让它们更容易留意和找回：

- 结算中，在擂台两侧保留对应角色的“结果 + 关键原因”。悬停左侧详情只替换左侧信息；右侧已执行反馈仍可见，反之亦然。
- 下一轮操作条只显示“上轮：造成 X / 受伤 Y”和“回顾 H”入口，避免把全部五拍挤进一句会省略的文字。
- 回顾仅在编排阶段且已有上一轮快照时可用。打开后展示五拍的双方结果与关键原因，来源是 `last_exchange_feedback` 的独立只读副本。
- 建议增加 `last_exchange_details() -> Dictionary`，返回已存在上一轮反馈的深拷贝；不重跑结算、不查询当前暗牌、不改变状态。
- H 打开/关闭，Esc 关闭，鼠标入口等价；回顾打开时拦截选牌、换牌、确认和拖动，关闭后恢复原计划与焦点。R 仍按原行为重开，并清除回顾。
- 重开、进入天赋选择和没有上一轮快照时，不展示旧回顾内容。回顾不是重播，不推进比赛时间。

示例原因沿用实际数据：“当时中距，需要贴身”“对手第 4 帧命中，你原定第 8 帧出手”“攻击落在闪避窗口之后”。结果与原因不由动画猜测。

### 4.5 天赋与轻量反馈

六选三继续使用现有网格。统一底板和字号；选中后清楚显示所选序号，底部三个槽按所选顺序连接。页面把“按顺序触发”说明保留一次。

天赋摘要由真实目录效果改写成“触发条件 → 收益”，完整原文可查；不增加虚构效果或组合推荐。战斗中只强调实际触发的天赋，常驻天赋不持续闪烁。

选中、撤销、拖动落位采用轻量反馈；动态效果放在最后一阶段，能关闭或减少。不要为表现效果启动预测计算或让隐藏信息提前出现在动画中。

## 5. 实施顺序与文件范围

| 阶段 | 优先级与产出 | 主要文件 | 验证方式 |
|---|---|---|---|
| A：先让牌看得清 | P0；关键字号、射程三格、独立预估标签、主次按钮；尽量保持现有位置 | `CardBoxer/scripts/tactical_hud.gd` | 复用现有 UI、forecast、feedback 检查；GPU 比较完整计划、十张手牌、待预测与错误状态 |
| B：统一五拍布局 | P1，依赖 A；顶部 136px 状态区、54px 对位槽、保留大手牌、同拍悬停与一致焦点 | `tactical_hud.gd`；必要的战术输入桥接 `arena.gd` | 有意义的交互和几何回归：十张手牌、全部命中区域、拖动/点击/取消、边界不重叠 |
| C：看懂上一轮 | P1，依赖 B；来源面板分侧处理、只读回顾及 H/Esc 等价操作 | `tactical_hud.gd`、`tactical_match.gd`、`arena.gd`；相关 UI/feedback 检查 | 射程打空、起手打断、防御过早、防御被绕过；回顾不改变状态、重开清空、无未来反馈 |
| D：统一构筑与细节 | P2，依赖 B/C；天赋页面、触发样式、轻量动效、说明排版 | `tactical_hud.gd`；需要时提取小型 HUD 绘制/布局辅助模块 | 六选三顺序、最长中文、连续撤销/重选、减少动态效果后的可读性 |
| E：验收 | 所选实施范围的最后阶段；真实 3D 渲染与输入验证 | `tests/tactical_capture.gd`、`tests/tactical_ui_check.gd`、`tools/verify_tactical.py`、`README.md` | 单项检查后运行现有 26 脚本完整回归；检查最终截图与真人或桌面输入 |

不需要引入 React、网页容器或重写现有战斗状态机。布局/绘制复用当前 HUD；仅为组件职责清晰而提取小模块，避免连带改造共享传统/实时 HUD。

针对纯配色或字号调整用渲染核验，不编写只镜像常量的测试。只有命中区域、输入、只读回顾、公开数据和状态显示发生变化时，才补对应行为检查。完整回归在最终整合时运行一次；出现新问题或新改动再按需复验。

实施中将 A–D 一并交付，以便 README 示例覆盖选牌、预估、战斗与回顾流程；完整回归和截图见实施记录。

## 6. 验收标准

- [x] 1600×900 逻辑画布上，双方五拍、全部十张手牌、撤回与开打同页可见；卡槽仍为 54px，手牌仍为 172px。
- [ ] 1280×720、1600×900、1920×1080、2560×1440 实际视口下不裁掉主要操作；非 16:9 使用既有等比缩放/留边。核对实际字形、按钮和选中抬升，不能仅比较坐标常量。
- [x] 玩家能从普通牌面直接找到招式、起手/伤害和射程；无需先悬停才能避免基本射程误读。
- [x] 每个结果标签能识别“预估”与“已执行”；`certain=true` 不显示成唯一伤害或已知暗牌，错误/等待不显示旧预测。
- [x] 编排中恰好三明两暗，暗牌没有独特分类色、数值、牌点或可推断身份的详情；玩家编辑不会改变敌方预览。
- [x] 灰度或颜色难区分时，射程、选中、风险、禁用和暗牌仍能靠词语、形状或边框识别。
- [x] 已有失败原因能在结算时读到，并在下一轮回顾找回；回顾无未来信息，打开/关闭/重开不造成重复扣血、换牌或计划变化。
- [x] 数字键 1–9/0、Shift+数字、Backspace、空格/Enter、P/R、鼠标及拖动保留等价操作；新增 H/Esc 不与既有快捷键冲突。
- [x] 所有卡牌与天赋详情包含完整目录效果；长中文可换行或单方向滚动，不因塞不下而静默截掉关键原因。
- [x] 真实 GPU 截图覆盖天赋选中、十张手牌、完整预测、暗牌详情、拖动、打空、打断、防御过早/被绕过、上轮回顾、暂停和比赛结束。
- [ ] 首次试排以 1080p 重要文字字形主体高度至少 18px、常规重要文字 4.5:1 为检查目标；另核对禁用文字 3:1 和动态背景。
- [x] 原有 26 脚本与新增 1 项 UI 行为回归全部通过。`forecast_status` 和分支状态均有行为覆盖。`AI/forecast P95` 基准未运行，不能据回归结果推定通过。

额外可用性检查：让首次试玩者指出当前距离、第一拍对应关系和一个失败原因，并观察其能否完成编排、修改顺序与找回上一轮原因。它是实施后的验证任务，不是本次已经测得的效果。
